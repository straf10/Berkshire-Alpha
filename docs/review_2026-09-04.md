## P0 findings — active risk today, 2026-09-04

### P0-1 — There is no terminal-day exit path when the book will not cross a net-credit close

**Sites**
- [walk_cap.py:52-64](agent/tools/walk_cap.py#L52-L64) — the `is_closing` branch
- [config.py:204-220](agent/config.py#L204-L220) — `WALK_CAP_CREDIT_SIGN_FLOOR`'s rationale
- [order_manager.py:265-267](agent/execution/order_manager.py#L265-L267) — `STRUCTURAL_CLOSE_REJECTS`
- [main.py:652-670](agent/main.py#L652-L670) — the only call site of `close_legs_individually`
- [order_manager.py:216-222](agent/execution/order_manager.py#L216-L222) — the cap terminator

**The rule.** Closing a LONG (debit) vertical takes the `structure_is_credit == False` branch,
so `cap = min(cap, WALK_CAP_CREDIT_SIGN_FLOOR)` = `min(cap, −0.01)`. The agent may therefore
**never pay anything to close a long vertical** — not a cent, ever, under any condition. The
stated invariant is right in general: a long vertical's value is bounded below by zero, so
paying to exit is an arbitrage-certain giveaway.

**Reproduced against the live 3 Sep book** (quotes from
[judgeEvidence.ts:80-87](web/lib/judgeEvidence.ts#L80-L87), 19:59:59Z):

```
closing legs:  SELL LLY260904P01165000  bid 2.72 / ask 17.19
               BUY  LLY260904P01160000  bid 5.58 / ask 10.11
net_mid      = −(2.72+17.19)/2 + (5.58+10.11)/2 = −9.955 + 7.845 = −2.11   (a credit)
net_natural  = −2.72 + 10.11                     = +7.39                    (a debit)
cap          = min(quantize(−2.11 + 0.70·(7.39 − −2.11)), −0.01)
             = min(+4.54, −0.01)                 = −0.01
limit        = min(net_mid, cap) = −2.11 → walks up in 0.05 steps → stops at −0.01
             → 42 steps → cancel → UNFILLED_REJECT → retry in 300 s
```

That is exactly the 3 Sep evidence: five walk segments, 250 replaces, no fill, last order
EXPIRED at 19:59:53. **The walker is not broken; it is doing precisely what it is told, and
what it is told cannot be satisfied by an inverted book.** The agent will run this same loop
today, roughly four times an hour, from 13:30 UTC to 20:00 UTC, and get the same result.

**The fallback that would work is unreachable.** `close_legs_individually` prices the short leg
at its **ask** ([order_manager.py:331](agent/execution/order_manager.py#L331)) and the long leg
at its **bid** ([order_manager.py:344](agent/execution/order_manager.py#L344)) — i.e. it crosses
the spread on both legs and therefore *can* fill against an inverted book. On the numbers above
it pays 10.11 and receives 2.72, a net 7.39/spread ≈ $2,956 for 4 spreads, against a mark the
account already carries at −$2,904. It is, to within ~$50, exactly what `scripts/flatten_lly.sh`
does by hand. But it is gated on
`result.status == "REJECTED" and result.reject_code in STRUCTURAL_CLOSE_REJECTS`
= `{MALFORMED_ORDER, CONTRACT_NOT_FOUND}`. An unfilled walk returns
`status="UNFILLED_REJECT"`, `reject_code=RejectCode.UNFILLED_REJECT`
([order_manager.py:219-222](agent/execution/order_manager.py#L219-L222)) — **not in the set.**
The one recovery path in the codebase for a spread that cannot be closed as a spread is
switched off in the only scenario that has ever occurred.

**Impact, stated as the position.** Spot closed 1160.62 — between the strikes. At today's
expiry, in the band spot is actually in (`1160 < S < 1165`): the long 1165P is auto-exercised
by OCC exception, the short 1160P expires worthless, and the account is left **short 400 shares
of LLY, ~$464,000 notional, on a ~$94,000 account, over a weekend.** The scoring snapshot is
already locked to EOD 3 Sep, so closing costs nothing in judged terms; the exposure is pure
downside with no scoring upside. This is a tail the risk stack exists to prevent and cannot,
today, prevent by itself.

**Remediation.** In order of how much I would trust each before 13:30 UTC:

1. **Operational, do this first, zero code risk.** Run `bash scripts/flatten_lly.sh` at the
   open. It is already written and already correct (short leg first, verify flat, then long;
   fallback ladder including `alpaca option do-not-exercise` on the long leg *after* the short
   is closed). See **Pre-Live Checks** for the ordering against the agent's own first tick.
2. **Widen the reject predicate** so an unfilled close escalates to legging out on the terminal
   day. Narrowest safe form, at [main.py:652](agent/main.py#L652):
   ```python
   terminal_day = unwind or dte <= 0
   escalate = (
       (result.status == "REJECTED" and result.reject_code in STRUCTURAL_CLOSE_REJECTS)
       or (terminal_day and result.status == "UNFILLED_REJECT")
   )
   ```
   `close_legs_individually`'s protocol (short leg first, abort untouched if it does not fully
   fill, never concurrent) is what makes this safe, and it is unchanged. Keep the escalation
   **gated on the terminal day** — on any other day "the walk did not fill" must stay "retry
   next tick", or every wide market becomes a cross-the-spread market order.
3. **Give `walk_cap` a terminal-day branch.** The zero floor's cost asymmetry inverts at
   expiry: it prevents a bounded giveaway (at most `width`) by accepting an unbounded
   assignment tail. Mirror the credit-structure closing branch:
   ```python
   if is_closing and not structure_is_credit:
       floor = (quantize(width_dec * WALK_CAP_MAX_FRACTION_OF_WIDTH_CLOSING)
                if terminal else WALK_CAP_CREDIT_SIGN_FLOOR)
       cap = min(cap, floor)
   ```
   `walk_cap` is pure and takes no clock, so `terminal` must be threaded in as a keyword from
   `_walk`'s caller — do **not** make `walk_cap` read a clock; `storage/read.py` calls it for
   the walk-timeline chart and must keep getting the same answer for a historical plan.
   Note this also changes what the chart renders for terminal-day closes, so pass the flag
   through `_walk_cap_for_trade` too or the chart and the walk will disagree — the exact thing
   [walk_cap.py:12-21](agent/tools/walk_cap.py#L12-L21) exists to prevent.
4. **Precedent worth copying:** `orphan_close_price`
   ([execution/assignment.py:38-49](agent/execution/assignment.py#L38-L49)) already has this
   escalation — `urgent = unwind or dte < DTE_FORCE_CLOSE` drops the limit straight to the bid.
   The single orphaned leg can escalate; the whole spread cannot. That asymmetry has no
   justification and is the shortest statement of this finding.

### P0-2 — `_is_priceable` still drops a zero-bid or all-zero-greek quote, which makes a held position un-exitable

**Sites**
- [market_data.py:146](agent/tools/market_data.py#L146) — all-zero greeks → drop
- [market_data.py:149](agent/tools/market_data.py#L149) — `bid_price <= 0` → drop
- [market_data.py:271](agent/tools/market_data.py#L271) — `fetch_leg_snapshots` filters on it
- [exits.py:56-58](agent/execution/exits.py#L56-L58) — `current_net_mid` returns `None` if **any** leg is missing
- [main.py:621-624](agent/main.py#L621-L624) — `exit_tick` `continue`s *before* `evaluate_exit`

**What the previous fix did and did not do.** review.md P0-1 was "the width check is in a
predicate shared by chain intake and position pricing." The remediation split
`_is_usable_for_entry` (width) from `_is_priceable` (everything else) and documented the rule
crisply: *"A quote must never be dropped for being wide once we own it."* Correct. But the
**other four rejection clauses stayed in the shared predicate**, and two of them fire routinely
on a position held to expiry:

- `bid_price <= 0` — an option that has gone worthless quotes 0.00 / 0.05. On expiry day this
  is the normal state of the OTM leg of any vertical.
- all-zero greeks — delta/gamma/theta/vega all round to 0.0 on a contract with hours to live.

Either one drops that leg from `fetch_leg_snapshots`. `current_net_mid` returns `None` for the
whole spread. `exit_tick` logs `"missing a live quote -- holding, retry next tick"` and
`continue`s — **and that check sits before `evaluate_exit`, so `UNWIND` and `TIME_STOP_2DTE`
never evaluate at all.** The position is not held because a rule said hold; it is held because
the code never got as far as asking.

This is not a hypothetical. `memory.md`, 2026-09-03 15:30, names it as the *likelier* of the two
abort criteria for that evening's watch:

> **19:30 watch has two abort criteria.** Bad price … and — likelier — NO order at all: a leg
> missing from `fetch_leg_snapshots` makes `current_net_mid` return None and `exit_tick` logs
> "holding, retry next tick" forever without ever reaching `evaluate_exit`.

The rationale for dropping a zero-bid quote is sound **for entry** (there is no meaningful mid,
and you cannot model a spread you cannot price). For a position you already own, a zero bid is
information — it says the leg is worth nothing — and throwing it away is strictly worse than
using it.

**Whether it binds on today's book:** probably not. The 1165P is ITM by 4.38 and the 1160P is
0.62 OTM, so both should quote a positive bid at the open. I am reporting it as P0 on the
strength of the failure mode (a silently un-exitable position, invisible to `evaluate_exit`),
not on a claim that it will fire in the next six hours. If the market gaps up through 1165 it
fires immediately on the 1160P.

**Remediation.**
1. Split once more. `_is_priceable` should reject only what genuinely prevents arithmetic:
   `latest_quote is None`, `ask_price <= 0`, `ask_price < bid_price`. A zero bid is priceable
   (`mid = ask/2`); zero greeks are priceable (they contribute 0 to the portfolio, which
   `build_exposures` already handles explicitly at
   [greeks.py:58-73](agent/risk/greeks.py#L58-L73)); null IV is priceable (nothing on the exit
   path reads `iv`). Move `iv <= 0` and the all-zero-greeks test into
   `_is_usable_for_entry` alongside the width check.
2. Make the remaining hole loud instead of silent. At
   [main.py:623](agent/main.py#L623), `logger.error` with the OCC symbol of the missing leg,
   and — see **P0-3** — write it to a state key so it is visible without log access.
3. Regression test: an open trade whose short leg quotes `0.00 / 0.05` with all-zero greeks
   must still produce a non-`None` `current_net_mid` and must still reach `evaluate_exit` with
   `unwind_triggered=True`. The existing suite has the wide-quote version of this test
   (review.md P0-1's remediation added it); it does not have the zero-bid version, which is why
   545 tests pass over this.

### P0-3 — A position going to expiry unclosed is recorded nowhere, and a failed tick reads as "no data" rather than "down"

**Sites**
- [main.py:1254](agent/main.py#L1254) — `await exit_tick(...)`, unguarded
- [main.py:1261-1263](agent/main.py#L1261-L1263) — `insert_health_sample(ok=True)` is the **last** statement in `management_tick`
- [main.py:1220-1228](agent/main.py#L1220-L1228) — the only `ok=False` sample, written on `CliUnavailable` alone
- [read.py:370-378](agent/storage/read.py#L370-L378) — an empty bucket is `no_data`, not `down`
- [main.py:664-670](agent/main.py#L664-L670) — `legged_close_pending`, the *only* precedent for surfacing a stuck position

**Three gaps that compound.**

1. **No "unclosed" signal.** `exit_tick` decides to close, walks, fails, logs at `INFO`
   ([main.py:642](agent/main.py#L642)) and moves on. Nothing is written to `agent_state`,
   nothing appears in `/status`, nothing appears in `/markgap` (which reports mark integrity,
   not exit failure). The system already has the right pattern one branch away:
   `legged_close_pending` is a state key written precisely so a stranded position is *"said
   loudly"* rather than silently parked. A spread that has failed N consecutive close attempts
   on its expiry day deserves at least as much.

2. **A mid-tick exception suppresses the health sample entirely.** `insert_health_sample(ok=True)`
   is the last line of `management_tick`, and the only `ok=False` write is on the narrow
   `CliUnavailable` path. Anything else that raises between them — `fetch_leg_snapshots` via
   `_tracked` (which re-raises by design,
   [main.py:110-115](agent/main.py#L110-L115)), a malformed `legs_json`, a `broker.submit_close`
   exception in the legged path — leaves **no sample at all** for that tick.

3. **`read.health_history` renders a sample-less bucket as `no_data`**, and its own docstring
   says `no_data` is *"expected for market-closed hours … rendering that as 'down' would make
   the strip mostly red."* Correct for closed markets; exactly wrong for a crashing tick during
   RTH. `supervised_loop` then catches the exception, logs it, sleeps 30 s and restarts
   ([main.py:1479-1484](agent/main.py#L1479-L1484)) — so the process stays up, the API keeps
   serving, and **the uptime strip stays green-with-gaps on the one panel judges are looking
   at.** A repeating deterministic failure is indistinguishable from a closed market.

**Impact.** The 2026-09-02 NVDA divergence (P1-5 below) is the empirical proof: a close that
happened at the broker and never reached the ledger was discovered *four days later, while
writing a document*. Today the same blindness applies to the inverse — a close that must happen
and does not.

**Remediation.**
1. Move the health sample into a `try/finally` so the tick always records its own outcome:
   ```python
   ok = False
   try:
       ...                       # everything management_tick does now
       ok = True
   finally:
       await storage_write.insert_health_sample(conn, HealthSampleRow(ts_utc=..., ok=ok))
   ```
   One caveat worth stating: if the failure is the DB connection itself, this write fails too —
   accept that, it is the one case where a DB-backed health signal cannot help.
2. Add an `unclosed_positions` state key, written by `exit_tick` whenever
   `decision.should_close` is true and the attempt did not fully fill: `{trade_id: {symbol,
   expiry, dte, attempts, last_status, last_limit, ts_utc}}`, cleared on a successful close.
   Publish it in `_publish_status` next to `entries_frozen`. It is ~15 lines, it is read-only
   from the API's side, and it is the difference between "we found this while writing a
   document" and "the dashboard said so".
3. Distinguish `no_data` from `down` inside RTH. `health_history` already has the session
   information it needs to do this properly, but the minimal version is: if a bucket lies
   inside `[open_utc, close_utc]` for a trading day and has zero samples, call it `down`.

### P1-1 — `_walk` does not treat `CANCELED` / `EXPIRED` as terminal

**Site:** [order_manager.py:195-222](agent/execution/order_manager.py#L195-L222)

`_walk`'s status ladder handles `FILLED`, `PARTIALLY_FILLED` and `REJECTED`; everything else
falls through to *"NEW / ACCEPTED -> replace one step further."* But `ALPACA_STATUS_MAP`
([schemas/execution.py:61-79](agent/schemas/execution.py#L61-L79)) maps `canceled` → `CANCELED`
and **`expired` → `CANCELED`**, and neither is in the ladder. So:

- The poll returns `CANCELED`.
- The cap test passes, so `broker.replace_order` is called on a dead order.
- `AlpacaBroker.replace_order` catches the `APIError` and re-fetches state
  ([broker.py:181-189](agent/execution/broker.py#L181-L189)) — by design, so a live-but-settling
  order is not abandoned. It returns `CANCELED` again, with the same id.
- `limit += WALK_STEP`, `step += 1`, loop.

It terminates only when `limit + WALK_STEP > cap` — for the LLY close, 42 iterations at
`WALK_REST_S = 15 s` ≈ **10.5 minutes of replaces against an order that no longer exists** —
and then `broker.cancel_order` raises on the already-cancelled order, which is *not* caught in
`_walk`, so it exits via `walk_to_fill`'s blanket handler, `_cancel_stranded` tries once more,
fails, and the result is `REJECTED / UNKNOWN` instead of the truthful `UNFILLED_REJECT`.

**Impact.** Two concrete costs, both live today:
- **It collides with the runbook.** `scripts/flatten_lly.sh` step 1 is `alpaca order cancel-all`.
  If a management tick's walk is in flight, that cancel puts the walk into the 10-minute futile
  loop, during which `management_tick` has not returned — so no health sample, no markgap
  publish, no status refresh, and the dashboard stalls while the operator works.
- **It mislabels the 3 Sep record.** Segment 5 (`19:48:33 → 19:59:53, 42 steps, EXPIRED`) is a
  DAY order killed by the closing bell; the walk kept replacing past 20:00 and booked
  `UNKNOWN`. Any post-mortem reading `reject_code` gets the wrong mechanism.

**Remediation.** Two lines, immediately after the `REJECTED` branch at
[order_manager.py:209](agent/execution/order_manager.py#L209):

```python
if state.status == OrderStatus.CANCELED:
    # Cancelled or expired out from under us (operator, cancel-all, or the
    # closing bell on a DAY order). The order is gone; replacing it is a
    # no-op that burns the rest of the walk against a dead id.
    return WalkResult(
        "UNFILLED_REJECT", order_id, limit, None, state.filled_qty, step,
        RejectCode.UNFILLED_REJECT, tuple(events),
    )
```

Use `filled_qty` from the state rather than 0 — an order can be cancelled after a partial fill,
and that partial is real risk that must reach `update_trade_result`.

### P1-2 — `exit_tick` has no per-trade exception isolation, and the legged close is not exception-safe

**Sites:** [main.py:620-687](agent/main.py#L620-L687),
[order_manager.py:306-360](agent/execution/order_manager.py#L306-L360)

`walk_to_fill` is exception-safe by explicit design — a blanket `except`, a documented
rationale, and `_cancel_stranded` to make it safe
([order_manager.py:85-148](agent/execution/order_manager.py#L85-L148)). `reconcile` holds the
same contract ([execution/assignment.py:113-133](agent/execution/assignment.py#L113-L133)).
`close_legs_individually` **does not**, and neither does the loop that calls it.

Two consequences:

1. **One bad trade blocks every later trade in the tick.** The loop body is unguarded, so an
   exception on the first of six open positions means the other five get no exit evaluation
   this tick — and if the cause is deterministic (a malformed `legs_json`, a leg whose OCC
   symbol no longer parses), every tick, forever. `supervised_loop` restarts the loop, which
   re-enters `exit_tick`, which fails on the same first trade. `MAX_CONCURRENT_POSITIONS` is 6;
   the book today is 1, which is the only reason this is P1 and not P0.

2. **A raise inside the legged protocol strands a leg with no record.** The protocol is safe
   against *rejection* (rule 2: if the short leg does not fully fill, abort and touch nothing)
   but not against *raising*. If `broker.submit_close` raises on the long leg after the short
   has filled, the function never returns, `LeggedCloseResult` is never constructed, and
   `legged_close_pending` — the state key whose entire purpose is to flag exactly this — is
   never written ([main.py:658-670](agent/main.py#L658-L670)). The book then holds a lone long
   option (defined risk, no obligation, so not dangerous) that no code path will ever close and
   no operator is told about. The trade row stays open, and the next tick rebuilds a 2-leg mleg
   close against a 1-leg position, which the broker rejects on `position_intent` — harmless, but
   it burns two rejected orders per tick and never converges.

**Remediation.**
1. Wrap the loop body: `for trade in open_trades:` → `try: ... except Exception: logger.exception(...); continue`. A position that cannot be evaluated must not cost the others their evaluation.
2. Give `close_legs_individually` `walk_to_fill`'s contract: a thin public wrapper with a
   blanket `except` that returns `STRANDED_LONG_LEG` carrying `short_fill` and
   `stranded_occ_symbol` when the short leg is known to have filled, and `ABORTED_SHORT_LEG`
   otherwise. The state write at [main.py:664](agent/main.py#L664) then happens on the raise
   path too.
3. `_open_trades` ([main.py:211-245](agent/main.py#L211-L245)) parses `legs_json` and
   `plan_json` for every row with no per-row guard — one corrupt row fails the whole query.
   `continue` on a row that will not parse, and log its `trade_id`.

`memory.md:344-345` flagged this as *"Open / to verify before `--live`"* on 2026-08-31 and it

**Impact.** Two failure modes with nothing between them and the account:
- **Wrong account.** If the deploy env's `APCA_API_KEY_ID` ever pointed at the old dev account

**Remediation.** One call, at the top of `scan_cycle`'s existing `try`, reusing the account it

if account.account_number != JUDGED_ACCOUNT_NUMBER or account.options_approved_level < 3:
    # write a HALT decisions row with gate_reason="ACCOUNT_IDENTITY_MISMATCH" /

The `CLI_UNAVAILABLE` branch at [main.py:858-868](agent/main.py#L858-L868) is the template: it

### P1-4 — `/health/history?hours=` is unclamped and can OOM the trading process

**Sites:** [app.py:139-142](agent/api/app.py#L139-L142), [read.py:343-385](agent/storage/read.py#L343-L385)

Every other bounded endpoint clamps: `min(limit, 200)` on `/decisions`, `/trades`,
`/assignments`, `/reflections`; `min(limit, 2000)` on `/equity/history`, `/greeks/history`.
`hours` is passed through raw, and `read.health_history` builds a dict with one entry per hour
*before* it looks at any data:

```python
buckets = {now_hour - timedelta(hours=i): [] for i in range(hours)}
```

`GET /health/history?hours=200000000` allocates 200 M datetime keys and a list each.

**Impact.** The API and the trading loop are the **same process** —
`asyncio.gather(serve_api(settings), supervised_loop(deps))`
([main.py:1556](agent/main.py#L1556)). An OOM kill on an unauthenticated GET therefore takes
down the trading loop, on a container Railway will restart with an unmanaged open position and
a `startup_reconcile` pass in front of it. The endpoint is public (`allow_methods=["GET"]` and a
CORS origin restrict *browsers*, not clients), and the dashboard URL is on the submission.

**Remediation.** `min(max(hours, 1), 168)` in the route, matching the clamping convention two
lines above it. Also worth capping the bucket construction in `read.py` itself so the invariant
holds regardless of caller — the route clamp is the fix, the function guard is the belt.

### P1-5 — Trade 4 is flat at the broker and open in the ledger; the reconciliation script was never run against prod

**Sites:** [docs/friction.md §4](docs/friction.md), [scripts/reconcile_closes.py](scripts/reconcile_closes.py),
[main.py:196-208](agent/main.py#L196-L208), [main.py:211-221](agent/main.py#L211-L221)

`docs/friction.md` §4 documents this precisely and honourably: NVDA (trade 4) was closed at the

`exit_tick` uses. **There is no evidence in `memory.md` or the git log that it was ever run

**Impact, beyond the reporting error friction.md already owns:**

**Remediation.**
```bash

AGENT_DB_PATH="<railway postgres DSN>" python scripts/reconcile_closes.py             # then apply
```
Dry-run first and read the output: step 3 only backfills when *exactly one* closing fill matches
the trade's qty, and reports-and-skips otherwise, so an ambiguous row will tell you rather than
guess. Do this **before** quoting any realised-P&L number in the submission.

### P1-6 — On a frozen-entry session, scan slots still preempt management ticks

**Site:** [main.py:1467-1471](agent/main.py#L1467-L1471)

```python
due = sum(1 for t in session.scan_utcs if now >= t)
if due > completed and now < session.cutoff_utc:
    await scan_cycle(deps, session, dry_run=deps.settings.dry_run)
else:
    await management_tick(deps, session)
```

`is_entry_frozen(now)` is True from 2026-09-03 onward and folds into `reduce_only`
([main.py:914-923](agent/main.py#L914-L923)), so `gate_will_reject_cycle` is True, the LLM
pipeline is skipped, and every candidate is rejected `REDUCE_ONLY`. But `scan_cycle` **still
runs in full**: two bar requests, 50 option-chain loads, the whole quant layer, a positions read
and greeks, then ~50 `decisions` rows that all say the same thing. `SCAN_OFFSETS_MIN` is
`(45, 135, 225, 315)`, so today that happens at 14:15, 15:45, 17:15 and 18:45 UTC. Each time it
costs the tick a `management_tick` — and because the loop sleeps `MANAGEMENT_INTERVAL_S`
afterwards ([main.py:1473](agent/main.py#L1473)), the exit attempt that would have run at 14:15
does not run until ~14:21+.

**Impact.** On the one day the agent's only job is exiting, roughly four exit attempts are
displaced by ~6 minutes each, and 50 chain loads per slot are spent to reach a conclusion the
same cycle already reached before the loop started. Real but bounded — P1 because of what day it
is, not because of the magnitude.

**Remediation.** Do *not* simply skip the scan: `completed` would stay at 0, `due > completed`
would stay true, and management would be starved forever. Advance the counter with a single row,
the way the `CLI_UNAVAILABLE` branch does:

```python
if due > completed and now < session.cutoff_utc:
    if is_entry_frozen(now):
        await _record_frozen_slot(deps, session, cycle_id)   # one HALT/REDUCE_ONLY decisions row
        await management_tick(deps, session)
    else:
        await scan_cycle(deps, session, dry_run=deps.settings.dry_run)
```
One row per slot keeps `_completed_scan_count` honest, keeps the funnel/dashboard truthful about
why the session had no entries, and hands the tick back to the exit path.

## P2 findings

### P2-1 — Two entry-price conventions for the same trade

[main.py:238](agent/main.py#L238): `entry_price = final_limit if final_limit is not None else submitted_limit`.
Meanwhile [main.py:1140-1142](agent/main.py#L1140-L1142) recomputes `max_loss_per_spread` from
`result.fill_price` on the explicit ground that *"plan.max_loss_per_spread is derived from
net_mid and is stale the moment the walk moves the fill off mid."* The same argument applies to
`entry_net_mid`, which drives `evaluate_exit`'s profit-target and stop-loss arithmetic and the
`realized_pnl` written at [main.py:673](agent/main.py#L673) — and it takes the *limit*, not the fill.
The `trades` row carries `fill_price`; nothing on the exit path reads it.

**Honest sizing of the impact:** on this account, essentially zero. `docs/friction.md` §3 tables
all seven fills, and every entry filled at exactly its final limit (DIA −0.55, ORCL −0.42, NVDA
1.49, LLY 6.65). The only divergence observed anywhere is a $0.02 price improvement on the NVDA
*exit* (−2.05 against a −2.03 submit, $8 on 4 spreads), which does not touch `entry_net_mid` at
all. This is a latent inconsistency, not a live error — the paper engine fills at the limit. It
becomes real the moment a fill is price-improved.

**Remediation:** `entry_price = fill_price if fill_price is not None else (final_limit or submitted_limit)`,
and say in the docstring why the fallback chain is in that order. Add a test pinning that a
price-improved entry produces a `realized_pnl` computed off the fill.

### P2-2 — `decisions` and its pipeline artifacts are not written atomically

Every writer in `storage/write.py` ends in its own `await conn.commit()`, and
`_persist_pipeline_artifacts` ([main.py:697-733](agent/main.py#L697-L733)) is a sequence of such
writers called *after* `insert_decision` returns
([main.py:1102-1105](agent/main.py#L1102-L1105)). A kill between them — or partway through the
artifact writes — leaves a `decisions` row whose debate, proposal and risk-vote rows are absent
or partial. `PgConnection.commit()` is a documented no-op under asyncpg's per-statement
autocommit ([db_pg.py:128-130](agent/storage/db_pg.py#L128-L130)), so this is the same on both
backends.

**Impact:** display and audit only. `/decisions/{id}` renders a decision with an empty reasoning
chain; `funnel`'s `debated` count under-reports; `_completed_scan_count` and the gate itself are
unaffected (they read `decisions` alone). The per-write commit for `trades` is *deliberate* and
must stay — [write.py:296](agent/storage/write.py#L296) explains that the row surviving a
`kill -9` between two walk steps is the entire point.

**Remediation:** wrap `insert_decision` + `_persist_pipeline_artifacts` in one transaction. That
needs a small addition to both adapters (`asyncpg`'s `conn.transaction()`; `BEGIN`/`COMMIT` on
aiosqlite) and it changes the write path on the last day of the competition — so my
recommendation is **do not ship this today**; record it and do it after the deadline.

### P2-3 — After a failed replace, the walk's local `limit` drifts above the broker's

[order_manager.py:224-226](agent/execution/order_manager.py#L224-L226) increments `limit`
locally, then calls `replace_order`. When the replace fails, `AlpacaBroker.replace_order`
deliberately re-fetches and returns the *old* state
([broker.py:181-189](agent/execution/broker.py#L181-L189)) — correct, and for a good documented
reason. But `_walk` keeps the incremented `limit`, so from then on it believes the resting order
is priced better than it is: it consumes its remaining steps against a price the broker never
received, terminates at the cap, and reports a `final_limit` that was never live. The direction
is safe (it never pays *more* than intended) but the walk gives up early and the record is wrong.

**Remediation:** rebind from the broker's answer — `limit = state.limit_price or limit` after the
replace — so the local view can never lead the broker's.

### P2-4 — `llm.py` has no 4xx handling

[llm.py:241-249](agent/tools/llm.py#L241-L249): after the JSON-mode negotiation branch (400,
once per provider/model pair) and the `429 / >=500` branch, everything else falls into
`data = resp.json(); text = data["choices"][0]["message"]["content"]`. A 401 (bad or expired
`FEATHERLESS_API_KEY`), a 403, a 404 on a renamed model, or a second 400 therefore raises
`KeyError('choices')`, which is neither `LlmUnavailable` nor `LlmValidationDropped`. It escapes
`_survivor`, is re-raised out of `run_llm_pipeline`
([pipeline.py:288-291](agent/agents/pipeline.py#L288-L291)), and is caught by `scan_cycle`'s
blanket handler ([main.py:979-991](agent/main.py#L979-L991)) — so the cycle degrades to
quant-only, which is the right outcome reached by the wrong route. Two costs: the traceback names
`KeyError`, not "your API key is rejected", and `_record` is never called, so the call is not
charged to the budget and leaves no `llm_calls` row.

**Remediation:** one branch before `resp.json()` — `if resp.status_code >= 400: await self._record(..., ok=False); raise LlmUnavailable(f"provider {resp.status_code} on node {node}: {resp.text[:200]}")`.
Note `resp.text` may echo the request; truncate and do not log the header block.

### P2-5 — Raw CLI stderr is published verbatim on a public endpoint

[main.py:862](agent/main.py#L862) writes `gate_detail=str(e)[:500]` where `e` is
`CliUnavailable`, whose message is the Alpaca CLI's stderr
([cli_bridge.py:65](agent/execution/cli_bridge.py#L65)). `decisions` rows are served in full by
`GET /decisions` ([app.py:65-67](agent/api/app.py#L65-L67)) — `SELECT *`

The secrets audit is otherwise clean: `.env` is gitignored and has never been committed (`git log --all -- .env` is empty), `.env.example` carries names only, and `/config` reads `agent/config.py`

**Remediation:** store a classified reason plus a redacted excerpt — strip anything matching
`(?i)(bearer|api[-_ ]?key|secret|token)\S*` before persisting — and keep the raw text in the

### P2-6 — The macro ladder is still inverted

[macro.py:181-196](agent/strategy/macro.py#L181-L196). review.md P1-3 made two claims: (a) the
`VWM_Z_STRONG` 0.75→1.00 raise went inert outside `NEUTRAL` because the other four bars were
hardcoded absolutes, and (b) the ladder was inverted, `RISK_OFF` (0.60) being *looser* than
`NEUTRAL` (0.75). (a) is properly fixed — the four bars are now multipliers of `VWM_Z_STRONG`.
(b) is **not** fixed, and the new docstring says so on purpose: *"Multipliers keep the original
relative ordering."* `RISK_OFF` is now `1.00 × 0.80 = 0.80` against `NEUTRAL`'s `1.00`.

So the agent still requires *less* momentum confirmation in a risk-off regime than in a calm one.
I am not calling this a bug — it is a preserved design decision, and preserving it was the
smaller change — but it is the kind of thing a judge asks about, and the docstring currently
describes the inversion as if fixing (a) had addressed it.

**Remediation:** decide, and write the decision down. If the intent is "risk-off means fewer,
higher-conviction trades", the multipliers should exceed 1.0 for `RISK_OFF` /
`DEFENSIVE_ROTATION`. If the intent is "risk-off is when momentum works, so lower the bar",
say that in the docstring and delete the sentence implying the ordering was the problem. Do not
change the numbers today — they are inside the preregistration freeze
([docs/preregistration.md](docs/preregistration.md)).

### P2-7 — Prompt-injection residual through the news chain

`Headline.build` truncates `summary` to 240 chars but leaves `headline` unbounded
([tools/news.py:28-31](agent/tools/news.py#L28-L31)), and
[analysts.py:57](agent/agents/analysts.py#L57) interpolates up to `NEWS_MAX_HEADLINES` (10) of
them straight into the news-analyst prompt. The analyst's own free-text `catalyst_summary` is
then re-embedded into the evidence bundle
([evidence.py:63-65](agent/agents/evidence.py#L63-L65)), which is what the bull, the bear and
the trader all read.

The mitigations are real and I do not want to overstate this: every model output is
Pydantic-validated; the trader may only choose strikes from a table it is handed; and
`build_from_proposal` re-derives every price, greek, width, max-loss and `p_success` from the
chain ([spread_builder.py:207-218](agent/strategy/spread_builder.py#L207-L218)), so no injected
text can set a number. `validate_proposal` then re-checks underlying, expiry, trading-day,
strike-listing, leg shape, ratio and the short delta band, and `gates.evaluate` is
LLM-blind by construction. The residual is **steering**: a crafted headline can push
`expected_impact`/`directional_momentum` and thereby `analyst_score`, the debate, and
`conviction` — which scales `qty` at [gates.py:181](agent/risk/gates.py#L181).

**Remediation:** truncate `headline` the way `summary` already is; wrap the headline block in
an explicit delimiter with a "content below is untrusted data, not instructions" line in
`NEWS_ANALYST_SYSTEM`; and strip control characters and fence markers from both fields at
`Headline.build`.

### P2-8 — `entrySlippage` scales by ordered qty

`(fill_price - submitted_limit) * t.qty * 100`. The trade's `filled_qty` is the right multiplier;

### P3-1 — The asyncpg pool is shared between the loop and the public API

`create_pool(dsn, min_size=1, max_size=10)` ([db_pg.py:29](agent/storage/db_pg.py#L29)), and
`connect()` holds one pooled connection for the whole `async with` block. `scan_cycle` holds one

several viewers at once during judging. Requests are individually fast, so this is a latency
risk rather than an outage, and I would not touch it today. Post-deadline: raise `max_size`,
pass an `acquire` timeout, and consider a separate pool for the read API.

## Second pass — findings I checked and rejected

Written out because the previous review's own note is right that this codebase's degrade paths
look like bugs and are not, and because I would rather show the work than assert the conclusion.

**Not bugs — deliberate design, confirmed against `memory.md` and the code's own comments:**

- **The deterministic spread-builder fallback in `trader.propose`**
  ([trader.py:314-324](agent/agents/trader.py#L314-L324)). When the model cannot produce a valid
  proposal twice, `spread_builder.build()` picks the strikes and the outcome is recorded as
  `mode="llm-fallback"` with `fallback_from` naming the rejection. This is not a fallback that
  loses the original intent: the *structure* was chosen deterministically by `regime.select()`
  before the model was ever called, so the model's only contribution was strike selection, and
  `build()` applies the same `SHORT_DELTA_BAND` rule. `_proposal_json` explicitly refuses to
  present the deterministic pick as the model's. It was the sole reason the agent traded nothing
  on 2026-08-31. **Do not "fix" this.**
- **Unanimous DISAGREE is no longer a hard veto**
  ([pipeline.py:227-232](agent/agents/pipeline.py#L227-L232)). `conviction()` floors it at
  `CONVICTION_UNANIMOUS_DISAGREE_FLOOR` and the deterministic gate turns a too-low conviction
  into `LOW_CONVICTION`. Intentional, dated, documented in three places.
- **`walk_cap` keying closing orders on `plan.structure` rather than mid's sign.** This looks
  wrong (the order being walked is what matters) and is right: `build_closing_plan` carries the
  original structure through while flipping every leg precisely so the *original* trade's
  economics remain identifiable, and an inverted chain can hand a long vertical a positive
  closing mid — a sign-keyed rule would then take the debit branch and authorise paying a full
  width. This is review.md P0-2's fix and it is correct.
- **`build_closing_plan` carrying `max_profit_per_spread` and `dte=0` through unchanged**
  ([exits.py:91-100](agent/execution/exits.py#L91-L100)). Documented as fields `SpreadPlan`
  requires and `walk_to_fill` never reads.
- **`is_entry_frozen` folded into `reduce_only` rather than given its own `GateReason`**
  ([main.py:917-922](agent/main.py#L917-L922)). Deliberate — one read site for the gate — and
  `/status` publishes `entries_frozen` separately so the freeze is never invisible.
- **The nickel escape valve in `_is_usable_for_entry`**
  ([market_data.py:169-170](agent/tools/market_data.py#L169-L170)). Looks like a hole in the
  width filter; is the fix for review.md P0-4's false positive (a 0.02/0.05 far-OTM wing is 86%
  "wide" and economically irrelevant, and coupling it to `DEGENERATE_CHAIN` dropped 36.5% of a
  perfectly tradeable SPY chain).
- **`_max_loss_from_fill`'s signed credit branch** ([main.py:185-193](agent/main.py#L185-L193)).
  `(w + f) * 100` is correct for both signs; the previous `abs()` understated the sign-flip case
  by `2f`. Verified by hand.
- **`_completed_scan_count` as `COUNT(DISTINCT cycle_id)`.** Survives a mid-session restart
  without re-scanning a completed slot; the `CLI_UNAVAILABLE` HALT row is what keeps a failing
  slot from repeating forever. Correct.
- **`db_pg.PgConnection._lock`** ([db_pg.py:89-106](agent/storage/db_pg.py#L89-L106)). Restores
  the statement-serialisation guarantee every `asyncio.gather` site was written against under
  aiosqlite. Correct, and the reason the concurrent analyst wave is safe on one connection.
- **`reflections` deliberately absent from `db_pg._HAS_ID`.** `insert_reflection` re-SELECTs its
  id rather than trusting `lastrowid`, with the reason in the docstring. Correct.

**Not bugs — arithmetic I convinced myself was a crash and is not:**

- **`gates.py:188` division by `per_contract_risk`.** I expected a `ZeroDivisionError` on a plan
  with `max_loss_per_spread == 0`. Unreachable: both builders return
  `NON_POSITIVE_MAX_LOSS` when `max_loss <= 0`
  ([spread_builder.py:173](agent/strategy/spread_builder.py#L173),
  [:262](agent/strategy/spread_builder.py#L262)), and the smallest positive value quantization
  can produce is `$0.50` per spread — leg mids are half-cent granular, so `width − |net_mid|`
  cannot land inside `(0, 0.00005)`.
- **`gates.py:196` division by `plan.width * 100`.** Unreachable for the same reason:
  `ZERO_OR_NEGATIVE_WIDTH` in both builders, and `_infer_structure` rejects equal strikes on the
  LLM path ([trader.py:139-140](agent/agents/trader.py#L139-L140)).
- **`sizing.py:48` division by `w_unit * L_UNIT`.** `max_profit_per_spread` is likewise
  guaranteed positive — `|net_mid| > 0` for credit (enforced by the sign check) and
  `width − net_mid ≥ 0.4·width` for debit (enforced by `MAX_DEBIT_FRACTION_OF_WIDTH`).
- **A debit structure priced at `net_mid == 0` slipping past `LIMIT_SIGN_MISMATCH`.** The gate's
  test `STRUCTURE_IS_CREDIT[...] != (net_mid < 0)` does admit `net_mid == 0` for a debit — but
  both builders reject it first with `SIGN_MISMATCH`
  ([spread_builder.py:152](agent/strategy/spread_builder.py#L152)), so no such plan reaches the
  gate.
- **`_reconcile` calling `equity_liquidation_price(mark, ...)` with `mark=None`.** Reachable only
  if an equity-triggered event had no matching position row, which cannot happen —
  `event.equity_qty != 0` implies the equity position exists in `held_by_symbol`. And if it
  somehow did, `reconcile`'s blanket handler returns `REJECTED` rather than raising.
- **SQL injection through `session_date` / `limit` / `hours`.** Every statement in `read.py` and
  `write.py` binds parameters; the two f-string `WHERE` clauses in `llm_usage` / `tool_usage`
  interpolate a *fixed* clause and bind the value. `db_pg._to_pg`'s naive `?`→`$n` rewrite is
  safe because no call site contains a literal `?` inside a string. Clean.

**The concurrency question in the brief, answered honestly:**

- **SQLite WAL contention between the loop and the API is not a production concern.**
  Production runs Postgres — `storage_db.connect` dispatches on the DSN
  ([db.py:28-31](agent/storage/db.py#L28-L31)) and `memory.md` confirms the Railway instance.
  The SQLite path is local dev and tests only, and there it is adequately handled:
  `busy_timeout=5000` and `foreign_keys=ON` on every connection, `journal_mode=WAL` set once by
  `schema.sql`, WAL readers never blocking the writer, and per-statement commits keeping write
  transactions short. The `daemon = True` fix on the aiosqlite worker thread
  ([db.py:33-49](agent/storage/db.py#L33-L49)) is the right fix for the CI hang it describes.
  The genuine atomicity gap on **both** backends is P2-2, and it is a display concern, not a
  money one.
- **The half-written `decisions` / artifact row the brief asks about is real** (P2-2) but the
  ordering is deliberately FK-safe — `decisions` first, artifacts after, `llm_calls` back-linked
  last — so the failure mode is a decision with a thin reasoning chain, never an orphaned
  artifact or a trade without a decision.

**Where I could not reach a verdict, so I am not claiming one:**

- **The sign of Alpaca's `filled_avg_price` on a multi-leg CREDIT close.** `close_trade` and
  `LeggedCloseResult.close_net` both assume a signed net (debit positive), and
  `docs/friction.md` §3 records the NVDA exit as `−2.05` and the ORCL exit as `+0.67`, which is
  consistent with signed. But those are the document author's normalisation, not a raw API
  capture, and `memory.md` (2026-09-03 15:30) flags this as explicitly **UNVERIFIED** with the
  right consequence: *"If it is unsigned, both the combined path and the legged path's
  `close_net` are wrong."* It is in **Pre-Live Checks** as a one-command verification, not
  reported as a defect.
